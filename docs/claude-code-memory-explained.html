PERSISTENCE ≠ CONTEXT ≠ TRAINING

记忆，不是大脑。是文件读取机制。

Claude Code 把值得跨会话保留的经验写成 Markdown。下一次先把目录索引放进上下文，再由模型按需打开相关正文。模型没有因为“记住”而修改自己的权重。

先记住这一句存在磁盘上
≠ 已装进上下文
≠ 一定被模型采用。截断通常发生在“读给模型看”这一步，不是把文件后半截删掉。
证据范围：前六章说明本机解包的 Claude Code 2.1.283 原生机制，普通文件记忆为主。使用 2026-10-03 的新会话 / resume 捕获和 2026-10-10 的后台维护实验；不是对所有未来版本的承诺。第七章为律枢最终讨论方案：索引与正文全部数据库管理，不使用独立记忆文件。实验与灰度分支、尚未实施的设计均明确标注。[S1][律枢方案]
01 / MAP

先分清三种“记忆”

A · INSTRUCTIONS

你写的项目说明

CLAUDE.md、CLAUDE.local.md、.claude/rules/。告诉它项目怎么做、有什么固定规则；可随 Git 共享。

本质：持久化的行为说明。
不是自动学习的笔记。
B · AUTO MEMORY

它写的长期笔记

MEMORY.md 是索引，feedback_testing.md 等是正文。保存用户偏好、纠正、非代码背景和外部资料入口。

本质：跨会话复用的文件。
本页的重点。
C · SESSION CONTEXT

本次对话与历史

聊天消息、工具结果、JSONL transcript、resume 和 compact。resume 恢复一段会话；compact 在上下文压力下压缩对话。

本质：会话连续性。
不等于给每次新会话装入所有旧聊天。
因此：“上次聊过”不等于“本次新会话知道”。要么 resume 那个会话，要么相关知识已经进入持久记忆，并在这次被召回。说明文件和记忆都是模型上下文，不是强制权限控制。[S7]
02 / LIFECYCLE

它如何从“记下来”到“想起来”

默认位置是 ~/.claude/projects/<project-key>/memory/。普通路径以项目 / 仓库为范围；同一仓库的子目录和 worktree 通常共用。不是给每个聊天新建一个记忆库；自定义目录与远端模式另有路径分支。[S2]

数据库集成测试使用真实数据库，不以 mock 替代。

**Why:** 用户曾遇到 mock 与生产行为不一致，
导致迁移问题未被测试发现。

**How to apply:** 写这类集成测试时，先准备隔离
测试数据库；单元测试不因此一律禁止 mock。

  1. 获得长期有效的信息

    用户纠正、确认非显然的做法，或提供背景。普通提示要求模型主动判断是否值得保存，不必等用户说“记住”。[S1]

  2. 先查重，再写正文

    检查有没有同主题文件；有则更新，没有才新建。普通分支用 Read / Write / Edit 等文件工具，不是向量数据库自动做语义 upsert。

  3. 另一步更新 MEMORY.md

    给正文加一行标题、链接和具体的用途提示。正文和索引是两次文件操作，不是“存一条就保证原子更新全库”。

  4. 新会话先加载有限索引

    捕获中：记忆行为规则在 system；索引在 user-role 的提醒块。只自动装入有限的索引，不把所有主题正文预先灌进去。

  5. 模型选择相关文件，按需 Read

    “数据库测试”命中索引后，模型读取 feedback_testing.md。description 和索引提示太泛，会增加漏读或选错的风险。

  6. 先核实，再采用；变化则修正

    记忆是过去的快照，不是当前事实保证。文件、函数、flag 可能已失效；新证据冲突时优先新证据，更新或移除旧笔记。

03 / LIMITS

限制到底卡在哪里？

200

MEMORY.md 最多加载的行数

第 201 行起不自动注入；内部空行也算行。
25,000

索引加载的 JS 字符串长度上限

不是 25,000 tokens，也不是严格的 UTF-8 字节数。

两道门取更早的一道。先截到前 200 行；若仍超过 25,000 个字符串单位，再在上限以内找最后一个换行，尽量保留完整行。第一行本身就过长且没有可用换行时，直接截到 25,000。裁的是给模型的副本。[S3]

对象 / 路径阈值真正的效果
普通 MEMORY.md
硬加载限制		200 行 + 25,000 JS 单位
哪道限制先到就在哪停		截断自动注入的索引；追加 WARNING。磁盘尾部还在，之后可用文件工具打开。并非全库最多 200 条。
索引写入后的检查
提醒，不是拒写		达到 80% 开始提醒
160 行 / 20,000 单位；建议缩到 70%		超出 200 行或 25,000 单位时返回带 Error 的重写提示，明确“write succeeded”。也就是写已成功，但下次读不全；建议目标为 140 行 / 17,500 单位。[S4]
普通主题正文
按需文件读取		不套索引的 200 行 / 25,000 上限普通捕获路径不自动注入正文；模型用标准文件工具按需读。仍受该工具的分页、结果和上下文预算约束，不能推成“任意大文件一次全读”。
CLAUDE.md 与导入文件
单文件读取护栏		超过 4 MiB 整份跳过
4,194,304 字节；200 行是建议		在此文件读取上限内，不按 MEMORY.md 的 200 行 / 25,000 规则截断。源码只在 type === "AutoMem" 时调用那个裁剪器；大说明文件另有性能警告。[S4]
CLAUDE.md 的 @ 导入
递归边界		根文件 + 最多 4 跳
根深度 0；深度 ≥ 5 跳过		限制导入嵌套，不是单文件行数；循环 / 已处理文件也会去重。拆成无条件 @ 导入改善组织，但仍会占用启动上下文。[S4]

有开关的维护分支		最多 200 个条目给提取模型的是文件名、类型、mtime、description 清单，不是预取全部正文；这不是最多只能保存 200 个文件。[S5]

单次最多 5 个候选文件		仅选择器预取路径；截断时提示用 Read 看完整文件。普通文件工具读取不因此被强制裁成 4 KiB。[S6]

“25KB”的精确含义：代码与文档的差别

  • 文档简写为 25KB；IDt → Klt 实际用 trimmed.length，也就是 UTF-16 code units。变量虽然叫 byteCount，这里却没用 Buffer.byteLength。
  • 普通英文字符、常见汉字通常各算 1 单位；很多 emoji 算 2 单位。9,000 个“记” = 9,000 单位，却是 27,000 个 UTF-8 字节，不会仅因超过 25,000 字节就在此裁剪。
  • 首尾先 trim()；再按 \n 数行。编辑器视觉自动换行不算新行，内部空行算。边界是 >：恰好 200 行 / 25,000 单位本身不超限。
  • 索引警告文字会附在裁剪结果之后，所以最终提醒块可以比 25,000 更长；25,000 限的是保留的原始索引，不含追加警告。
展开：还有哪些数字不能误读为“自动截断”？
  • 一行约 150 / 200 字符：保存提示建议一条索引约 150 字符内；裁剪警告建议一行约 200 字符内。都不是逐行硬裁剪阈值。
  • 40,000 与 120,000：说明文件性能警告的字符阈值下限，不是截断点。单文件警告阈值 = max(40,000, 按模型窗口估算的 5% 字符预算)，合计阈值 = max(120,000, 单文件阈值)。与 4 MiB 读取护栏分开。
  • 选择器的 61,440：QEr 在已累计预取正文达到该值时停止发起新召回；虽然叫 totalBytes，s5o 累加的是正文 .length。这是启动新预取前的检查，不是每次装入严格裁到 61,440。此灰度路径不能当作普通记忆的全局硬预算。
  • 4 条 pinned、生成清单 200 / 50 条：来自 stone-shell 等其它条件分支，不是本次已捕获普通索引模式的普遍保证。
  • 4 MiB：启动索引走的普通 KSe 文件读取也有这道护栏。极端巨大 MEMORY.md 会先被整份跳过，根本走不到 200 行 / 25,000 裁剪。实验台仅模拟裁剪器，不模拟该文件读取护栏。

04 / TRY IT

亲眼看：文件没删，模型少看了什么

修改左侧文本，右侧按该版本索引裁剪算法实时显示可加载的内容。这个实验完全在页面内运行，不读取、不改动你的真实记忆文件。

试一个边界
计入 0 行0 JS 单位0 UTF-8 字节
保留 0 行0 JS 单位源文本仍完整
自动加载 100%留在磁盘、未自动加载 0%

只复现 IDt 的 trim → 200 行 → 25,000 单位裁剪，不模拟 Markdown 前处理、4 MiB 读取护栏或追加 WARNING。空字符串在源码计数器里算 1 行；界面显示为空。状态提醒按原文是否超过阈值判断，因此原文两项都超限时会标两项，即使保留量实际先被行数卡住。

展开：裁剪器的等价逻辑
text = source.trim()
overLines  = countNewlines(text) + 1 > 200
overLength = text.length > 25_000    // JS UTF-16 单位

kept = overLines ? first200Lines(text) : text
if (kept.length > 25_000) {
  lastBreak = kept.lastIndexOf("\n", 25_000)
  kept = kept.slice(0, lastBreak > 0 ? lastBreak : 25_000)
}
// 原文件不动；实际实现还会在 kept 后附加警告。
05 / MAINTENANCE

“自动记忆”不只有一种自动

普通主对话主动维护、后台增量提取、Auto Dream 是三条不同路径。后两条在同一 CLI 内部 fork 父对话，继承上下文和工具表，再由专用权限回调限制执行；不是每写一个文件就启动一个去重函数。[S5]

01 / MAIN CONVERSATION

主对话：当场记笔记

普通记忆提示让主模型判断什么值得跨会话保留，按需读写文件、查重、更新索引。

  • 学到角色、偏好、纠正或非显然的正向确认时主动保存。
  • 用户说“记住”时保存适合长期记忆的信息。
  • 是否真的调用工具，仍取决于模型执行；没有 100% 遵守保证。
02 / GATED EXTRACTION

后台提取：补漏

主 turn 结束后检查 gate 和增量窗口，提取最近新增对话值得保存的信号。

  • 需 passport_quail gate；headless 另需 slate_thimble。
  • 频率由配置控制，源码 fallback 为 1；不是固定每一轮必跑。
  • 至少一条合格非 meta 用户文本，空白切词 ≥ 3。无空格中文可能不过此过滤，主对话保存中文不受这一条件限制。
  • 主对话已经发出记忆 Write / Edit 时会跳过该窗口；失败的 Edit 也可能被算作“已写过”。
  • 最多 5 个 agentic turns，不是最多 5 次工具调用；headless 退出默认最多等 60 秒 drain，不是每个任务 60 秒超时。
03 / AUTO DREAM

Dream：跨会话整理

turn 结束时判断是否到期，再整理已有记忆与近期活动信号；不是每 24 小时自启动的守护进程。

  • 需可用性 rollout + 用户开关；sdk-cli / sdk-ts / sdk-py 入口排除。
  • 源码默认距标记 ≥ 24 小时、≥ 5 个更新会话；服务端可覆盖，排除当前会话。
  • 扫描节流 10 分钟，有 PID 标记锁。
  • Orient → Gather → Consolidate → Prune & index。
  • 默认最多 50 个 agentic turns。界面保留最近 30 轮不等于只执行 30 轮。

别把“源码里有”当作“你的机器已经在跑”

2026-10-10 的本机缓存快照：后台提取两个 gate 都是 false；Dream enabled:false，配置 minSessions:3。这个 3 与源码 fallback 的 5 必须分开。缓存可能变化，本页不声称当前 rollout 状态。

24 个正向 / 负向机制用例使用隔离配置和本地假 API；Dream 正向还使用合成 desktop 入口。它们验证调度与工具边界，不是“真实模型一定会整理得好”。普通 claude -p 的捕获入口是 sdk-cli，即使 gate 打开也不跑这条 Dream。

展开：后台写完，主对话如何知道？还有什么可靠性限制？
  • 后台成功改文件后同步主对话读缓存，并排队 memory_update；下一模型请求提醒“已加载的旧副本过期，需重新 Read”。不会把所有新正文自动塞回 system。
  • 普通后台 Write / Edit 只准记忆目录内、通过保护检查的 .md；可读工具仍查显式阻断和目录限制。父工具表里即使看见 Agent / MCP，执行权限也不因此放行。
  • 主对话、提取器和 Dream 的普通本地文件分支，没有全库 CAS 原子合并、整库事务回滚或确定性的语义查重阈值。部分写入失败时，之前成功的文件可能已落盘。
  • Dream 修正旧记忆、合并重复项、缩短索引，但不在这条整理任务内修改 CLAUDE.md。正常完成即使没改任何记忆，也会推进冷却标记。
06 / PRACTICE

怎样写，才更容易被正确用上

user

你的角色、经验、长期协作偏好。

feedback

纠正与确认过的做法；包含原因与适用范围。

project

代码推不出的目标、动机、约束、截止日期。

reference

到哪里找最新信息，而不是复制一份易过期内容。

01

把索引当目录，不当正文

一行一条具体“检索钩子”；细节放主题文件。不要只写“重要”“偏好”“注意事项”，要写“何时需要这条经验”。

02

重要条目靠前，但不要迷信排序

尾部越界会失去启动可见性。先合并重复项、迁移细节；目录没有列出也不代表正文被删，显式查文件仍可能找回。

03

一主题，写 Why 和 How to apply

“不用 mock”过于绝对；“数据库集成测试不用 mock，原因是……，仅此场景适用”才能让未来的模型正确迁移经验。

04

不存项目已经能回答的内容

普通提示排除代码结构、Git 历史、调试修复配方、CLAUDE.md 已写内容和临时进度。即使用户说“记住”，也要提炼真正非显然、跨会话有用的经验。

05

记录时间，使用前检查现状

项目背景里的“下周四”应转为绝对日期。老记忆引用文件 / 函数 / flag 时先确认仍存在；旧信息不是当前事实的证明。

06

保存成功，要看实际文件操作

“我会记住”不等于已经落盘。检查主题正文和索引是否都更新；去重 / 修正依赖模型，没有保证零遗漏、零矛盾的存储魔法。

怎么检查：原生终端 /memory 可打开记忆目录、说明文件和开关；/context 可查看已加载的说明。关闭自动记忆可用 autoMemoryEnabled:false 或 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1，但这不等于关闭 CLAUDE.md，也不等于禁止所有文件工具读取。[S2][S7]
记忆会自动过期删除吗？

没有在普通分支中发现“超过 200 行就删除旧记忆”或固定年龄 TTL。会话 transcript 的清理与记忆文件是两套事。记忆保留到用户或模型修改 / 删除；模型被要求在有新证据证明错误或过期时修正或移除。Dream 的语义修剪也不是按容量静默删尾部。[S1][S7]

这是向量检索或自动 embedding 吗？

本次已捕获的普通索引模式不是：有限索引进入上下文，模型用文件工具按相关性读主题。源码另有 memorySelector 的灰度自动预取路径；不能因此把普通模式描述成始终运行的向量搜索，也不能断言所有未来分支都采用相同检索机制。[S6]

子 agent 会自动继承主 agent 的所有记忆吗？

一般子 agent 不默认装入主对话的 auto memory。定义了 memory:user|project|local 的 agent 有自己的目录：~/.claude/agent-memory/<name>/、.claude/agent-memory/<name>/ 或 .claude/agent-memory-local/<name>/，其 MEMORY.md 也走索引裁剪。后台维护这样的 conversation fork 是例外，会继承父上下文；“独立子 agent”和“fork”不能混为一谈。[S3][S5][S7]

本地存文件，是否意味着内容永不发送给模型服务？

不是。存储可以是本地的，但被注入的索引和工具读出的正文会成为正常模型请求的一部分。本次假 API 捕获直接验证了这件事；别把“机器本地存储”误解为“永远只在磁盘上”。

在 cc-webui 里看到的统一项目记忆，也是这套限制吗？

不是同一存储，但同样有索引预算，并非无限索引。启用 CC_WEBUI_PROJECT_MEMORY_ENABLED 后使用独立 Memory MCP / DB 索引 / 正文版本，且给 Claude 子进程设置 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1。原生后台任务不会代它整理。

  • 自动快照最多 200 条记忆，不是 200 行；编码 JSON 最多 24,980 个 JS 字符串单位，按完整条目截断。
  • 索引按更新时间倒序，只带元数据。未展示条目仍保留，快照标记 truncated:true，模型可用 list / search 补查。
  • list 每页最多 100 条；search 每次最多 20 条，覆盖整个授权项目，但只匹配名称和描述，不搜正文。
  • 单条记忆含生成的 frontmatter 硬上限 32 KiB；超限拒绝保存，不静默截断正文。

所以库变大后，较旧记忆可能不再自动出现；模型是否主动补查仍影响召回，不能保证零遗漏。此说明没有修改任何运行时配置。[S8]

07 / FINAL DESIGN

律枢 × Claude Code：数据库记忆方案

最终讨论方案 · 尚未实施2026-10-13 · 结合当前源码与本次讨论整理

一个统一记忆库，两条分类轴，PostgreSQL 是唯一真相。索引和正文全部在数据库中管理；不再选择“单独的 Markdown 文件”方案。借鉴 Claude Code 的短索引、按需读正文与主动记忆规则，替换律枢复杂的召回／学习流程，但保留实体授权、版本与出处。本章是实施蓝图，不代表已改代码、迁移数据或发布。[S9][S10]

两轴分类数据库结构实体索引工具与行为安全边界迁移步骤验收标准

判断：律枢复杂的主要不是存储，而是记忆周围叠了太多决策流程。

用户真正关心的是“它到底记住了吗？”和“下次到底会不会用？”。优化目标应是可理解、可追溯的单一读写链，而不是再往旧状态机上增加一套记忆。

CURRENT / 当前源码不同职责叠在多条链上
  • 召回：授权过滤 → 候选超过 35 条时另起模型挑选 → 最多 6 轮、默认 30 秒超时 → 失败确定性回退。没超预算不调用 picker。
  • 保存：模型要理解 scope、rule / fact、long_term / one_off、risk，以及新建、印证、冲突、确认和取代。
  • 事后学习：对话提炼、改稿提炼、改稿质量检查各有输入、进度与重试。
  • 维护：候选核对、日终确认、跨律师归纳、共享复核叠加。每层都有来由，但整体生效路径不直观。
TARGET / 最终目标数据库唯一真相
当前律师／客户／项目 + host 授权
        ↓
查询 PostgreSQL，生成有限实体索引
        ↓
主 Agent 按需 list / search → read 正文
        ↓
通过 save / delete 保存、纠正或停止使用
        ↓
统一记忆服务提交数据库事务
记录、版本、出处一致；目录由查询生成

取消前置“挑记忆模型”，让正在处理任务的主 Agent 判断相关性。可以减少一个前置模型等待点，但不等于主模型总用量必然下降，也不保证零漏召回；要用律枢任务实测。模型不连 PG，不拿 DSN。

一、两条分类轴：归谁 × 讲什么

实体维度与业务维度是两个独立字段，不是二选一，也不按它们拆出多个记忆库。分类负责组织与理解；谁能访问、何时可生效、能否跨客户共享，是另外的服务端判据。

ENTITY / 实体归属这条记忆归谁
  • 律师：某位律师的长期习惯、工作方法与协作背景。
  • 客户：围绕某个客户的要求、沟通方式与背景。
  • 项目：仅适用于某个项目的目标、方法与约束。

律所 ID 是每条记录必带的租户隔离键，不要求用户把“律所”再选成第四种日常记忆实体。旧所级资产仍需保留与映射，不因新分类只有三种实体就被删除。

BUSINESS / 业务内容这条记忆讲什么
  • 偏好：希望结果是什么样，例如表达风格、文书呈现方式。
  • 做事方式：工作过程怎么开展，例如核对顺序、沟通方式。
  • 背景与约束：影响工作的稳定事实、目标、范围与限制。

不生搬 Claude Code 的 user / feedback / project / reference 四个标签；保留其主动保存和质量规则，换成律枢业务语言。交叉内容选主类别，适用条件写正文，不追求多重分类组合。

实体归属业务类别记忆示例 · 合成数据
张律师偏好意见书先给结论，再展开论证。
张律师做事方式审稿先核对原始材料，再提出修改。
甲客户做事方式材料疑问统一汇总给指定联系人。
某项目背景与约束本项目仅做内部梳理，不对外出具意见。

边界例子：“张律师给甲客户的意见书，要先结论后分析”

可以归属甲客户、分类为偏好，但必须保留“仅适用于张律师”的限定，不能自动变成所有律师对甲客户的要求。作者是谁也不等于适用律师是谁；来源、适用限定与实体归属分别记录。客户背景里含单案事实时，还要收窄到对应项目，不能默认为客户永久事实。

二、数据库管理全部内容，不存在第二份文件真相

优先演进现有 memory_item 与历史／出处结构。下面是逻辑字段分工，不是已经执行的 DDL，也不要求为了字段分组新建多张表。正文以数据库中的 Markdown 文本保存，属于记忆记录，不是单独的 .md 文件。

字段组逻辑字段责任与规则
稳定身份id稳定记录 ID；迁移保留旧 ID／ref 或可核对映射，不靠标题或文件名当身份。
租户与实体workspace_id
entity_type / entity_id		实体类型为 lawyer / client / project；host 校验实体存在、属本所、当前可见且可写，不信模型声明。
业务分类business_type偏好／做事方式／背景与约束。旧 rule / fact 不机械一对一映射；需结合正文和来源，未判清不强行自动分类。
检索信息title / description标题命名主题，描述说明什么时候用得上。自动索引只携带这些元数据及必要的 ID、分类、版本。
正文body完整 Markdown 文本。偏好／方式说明具体做法、Why、How to apply 与例外；不另维护 frontmatter、正文文件或 MEMORY.md。
版本与生命周期revision / state
创建／更新时间		业务上区分有效、待核对、停止使用；不把旧状态与取代链粗暴丢弃。更新检查 expected_revision；状态有效不等于允许共享。
授权与可信来源适用律师、共享批准、风险／冻结判据
消息／对话／KnowledgeSlice／改稿出处		后台管理并复用现有约束，非用户第三套分类。出处由 host 验证并绑定；原话、diff 与完整历史证据保持私有。
“实体索引”不是额外存一份正文：它是从当前数据库记录生成的目录投影。记录保存成功后，再次查询自然得到新目录；不需要模型“先写正文、再补索引”，也不为每位律师／客户／项目建一张独立表或独立数据库。
两个“索引”不要混淆
  • 记忆目录索引：给模型看的标题、描述、分类、版本清单，由查询生成。
  • 数据库查询索引：用于提高查询效率，例如以租户、实体、状态等字段设计 SQL 索引；它不承载第二份记忆内容。
  • 正文、版本和出处使用同一事务保持一致。纯遥测与业务凭据区分：遥测失败不阻断工作；保存一致性或必要共享批准失败必须回滚，不能报保存成功。
  • 可复用已有版本／证据表，不为“数据库化”再引入独立文件仓、双写缓存或通用事件框架。若后续加缓存，缓存不能成为授权或内容真相。

三、实体索引按当前轮生成，正文按需读取

  1. host 固定身份、归属与工具能力

    根据当前运行者、对话 kind、客户和项目确定本轮允许的实体。模型可使用这些授权实体的引用，不能靠传入任意 entity_id 扩大范围。

  2. 数据库先授权过滤，再排序与截断

    同所过滤之后仍查实体可见性、适用律师、当前生效状态和共享复核。范围内目录按实体分组，条目使用稳定确定性顺序；不把现行 picker 或“每层三条”的配额再复制进新链。

  3. 只注入有预算的元数据快照

    快照含授权实体、可见条目数、已显示数和 truncated；总数不能泄露不可见记忆。仅在完整条目边界截断，不发正文、不发全所客户总目录。索引是当前轮背景数据，不提升为能覆盖执行规则的指令。

  4. 主 Agent 决定读什么

    看到相关标题／描述后调用 read。索引不足时 list 翻页或 search；搜索匹配标题、描述及正文，但先返回元数据，再显式读完整正文，不增加前置选记忆模型。

  5. 每轮与续聊刷新，读写再次验权

    新会话、resume、换 provider、后续普通轮次都获取当前快照。旧快照不能替代当前权限；归属或授权改变时旧能力失效，下一轮重新签发。历史保留不等于旧记忆仍可用。

INDEX SNAPSHOT / 逻辑示例数据来自查询，不是索引文件
当前授权实体：张律师、甲客户、某项目

[张律师] 已显示 1 / 当前可见 8 条
  id: …  类别: 偏好  revision: 3
  标题: 意见书表达顺序
  描述: 写意见书时先结论再论证，解释原因与例外

[某项目] 已显示 1 / 当前可见 5 条
  id: …  类别: 背景与约束  revision: 1
  标题: 委托工作范围
  描述: 本项目的工作范围及不可超出的交付边界

truncated: true → 需要其它条目时分页／搜索
body: 不在快照中 → 用 read 获取数据库正文
预算与长正文：借鉴原生机制，不混淆单位或冒充已定参数
  • 新方案必须有条目数、编码长度／上下文预算和单次工具返回上限；这限制一次给模型多少内容，不是最多能保存多少条。
  • Claude Code 的 200 行／25,000 JS 单位与 cc-webui 的 200 条／24,980 JS 单位是两种实现。律枢为 Go 服务，须明确字节、rune、UTF-16 单位或 token 估算的具体口径，不能把它们叫同一个“25KB”。
  • 具体首版参数尚未在本次讨论中定值。可以参考 cc-webui 预算，但需由律枢实际语料与延迟／召回评测确定；这不影响已经确定的全数据库存储和两轴分类。
  • 超出快照的条目仍可通过授权分页／搜索读取。正文默认按完整记录读取；超大记录如需分段，必须给出总量与后续游标，不能悄悄截尾或把半段说成全文。
  • 新写入超限应明确拒绝并要求按主题缩短／拆分；旧记录迁移不得直接按新上限截断。不得为了追求小索引自动删除旧记忆。

四、五个工具、一处写入、同一套行为规则

工具语义作用必须保证
list分页列当前授权实体的元数据；可按业务类别筛选不默认返回正文；游标与 total 只覆盖当前可见集合。
search在授权范围搜标题、描述及正文，返回命中记录元数据授权先于 LIMIT；不把不可见正文片段带进搜索结果。
read按稳定 ID 读取当前完整正文和 revision每次重新验权／状态；未知与不可见的返回不用于存在性探测。
save新建或更新：实体引用、业务类别、标题、描述、正文更新须 id＋expected_revision，写入绑定幂等 operation_id。host 核定实体与出处，单事务保存记录／版本／证据；重复请求不重复沉淀。
delete停止以后使用指定记忆，而非擦除全部历史验权、验版本并留失效原因与证据；不绕过离职冻结、既有规则管理权或既定审计／产品保留要求。

名称表示目标工具语义，不是已经上线的协议。模型经现有受限 MCP → 主服务 → PG 调用，不直接发 SQL，不拿数据库凭据，也不通过 Read / Write / shell 绕过记忆服务。

启用律枢托管记忆后，不允许原生记忆另起一套并行库：Claude 子进程使用已验证的 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 关闭原生自动记忆；其它 provider 由受管适配器确认只装配本平台索引与工具，不继承个人记忆来源。限制仅作用于律枢运行，不修改个人 CLI 全局配置。

A

保存前查重，更新已有主题

不要用“写过一次”或“重复出现次数多”自动证明长期正确。先搜索、读取同主题，能更新则更新；并发版本冲突后重读，不强制覆盖。

B

只保存能跨会话改变行为的信息

明确长期偏好、做事方式、稳定背景与约束才入库。临时计划、进度、模型自我推断和单案修改不自动当长期通则；相对日期变绝对日期。

C

记忆是旧背景，不是当前事实保证

使用前核对新证据与适用条件。纠正后更新，错误且无可保留内容时停止使用；不依据旧聊天复活失效记忆。

D

保存、采用、共享三件事分开

工具如只确认记录为待核对，就显示“已记录，待核对”，不能说“以后已自动采用”。风险与来源要求由服务处理，不让模型给自己的内容盖共享批准章。

律师看到的交互保持简单：本次读了什么、记了什么、改了什么、哪些确实需要核对。业务分类只有“归谁＋讲什么”；来源、版本、生效判据与共享批准由后台管理，完整敏感载荷仍仅给有权限的观测面。

迁移核心思路，不照搬实现外壳

部分建议取舍为什么
索引与召回确定性索引＋分页／搜索在授权过滤后生成有限快照，超限明确标记；不在首答前额外起 picker。预算可先参考 cc-webui，但最终须明确本系统单位、条数和超限行为，不直接宣称已采用其阈值。
模型工具list / search / read / save / delete收敛模型面对的交互，不让它掌握整套印证状态机。工具命名是目标接口；是否可调用和能改变什么，仍由服务端能力与写闸决定。
正文结构一主题一条数据库记录，两轴分类实体为律师／客户／项目；业务为偏好／做事方式／背景与约束。正文保留 Why、How to apply 和适用条件，不复制原生四类型标签当律枢分类。
底层存储索引元数据与正文全部在 PostgreSQL不新增 SQLite、不落独立 Markdown 记忆文件、不用 cwd 建库、不维护真实 MEMORY.md。实体目录由记录查询生成，不是第二份内容真相。
搜索复用正文关键词匹配不必照搬 cc-webui 只搜名称／描述的限制；先返回索引，随后显式读取全文。范围过滤仍须先于搜索结果 LIMIT。
更新与遗忘版本冲突检查、可追溯失效保存成功后才能宣称记住；“忘记”停止以后使用，保留必要历史证据。不要直接复制 cc-webui 删除全部正文版本的语义。
后台学习所有来源写入同一服务对话与改稿学习不再形成另一套生命周期；明确长期偏好与从 diff 推测出的经验仍区别处理。保留反馈／改稿证据与必要核对，不把纯个案修改直接自动生效。
强制规则与参考资产不并入相关性竞争草稿态、交付限制等进入常驻执行规则；reference 经验清单、Skill 与母版保留各自职责，不因为“统一记忆”就随意合库。首版不移植 Dream。
关键：模型负责判断“哪些信息值得整理成记忆”；host 决定“能不能写、归到哪里、能不能生效、能不能跨客户共享”。这些判断可以集中在服务内部，但不能因工具参数少了就消失。

五、必须保留的安全与资产边界

01

按业务身份授权，不按目录共享

律所隔离之外，仍查律师、客户、项目、对话可见性。同所同 cwd 不证明可读对方记忆；换 provider 也不能改变授权范围。

02

consult 只读，正式工作按写闸学习

保留当前对话 kind／归属的服务端判据。对话归属变化时旧 capability 失效，不把一次签出的能力当永久授权。

03

客户事实不混进跨客户通用规则

广 scope、active、律师采用都不等于客户中立。共享批准继续绑定完整正文与归属，内容修改后重新检查。

04

离职只读，修改和学习能追溯

保留离职冻结、KnowledgeSlice、消息／文件 diff 出处和必要历史。不批量把旧候选变成已采用，也不让模型自评代替隐私或高风险核对。

六、最终一套机制，实施三步切换

  1. 先替换读取链

    先盘点旧 memory／reference／所级资产及出处，制定两轴字段映射，不自动改写正文或生效状态。在数据库兼容读取层保留原授权过滤，生成有限实体索引；改工具教学与主 Agent 按需读取，取消前置 picker。同步 run-context 的同轮来源，避免聊天看到一套、技能拿到另一套。

  2. 再统一写入与学习

    主对话保存、对话提炼、改稿学习全部接同一新服务；记录、正文、版本、出处在 PG 事务内更新，目录不双写。律师反馈／diff 仍落可追溯证据，推测经验仍需必要核对。旧生命周期由新入口承接，不并行写两套记忆。

  3. 最后迁移数据、退役旧流程

    保留旧 ID／ref、出处、采用状态、共享批准与历史映射；旧所级资产明确去向，不因为不属于三种日常实体就丢弃。显式备份并核对旧学习队列／在途批次，切换后停用旧写入与旧注入。冻结／兼容保留旧结构直到验收；回滚不覆盖切换后新增业务，不自动整库 restore。

实施地图：优先改哪里，不是现在已修改
  • server/internal/service/memory.go：用授权后的有界索引、分页和搜索替换 MemorySelected 的 picker 分支；同时保持全文读取语义。
  • server/internal/runner/memory_pick.go：读取链切换并验证后退役前置模型选择，而不是仅把超时调低。

七、验收看实际行为，不只看工具是否成功

  • 记住后找得回新会话、换 provider，仍能读取正确范围的正文并实际采用。
  • 纠正后不再用旧版更新与冲突有明确版本语义，旧历史不能复活失效记录。
  • 忘记后不再召回停止使用与保留历史证据分别验证，不宣称旧聊天被擦除。
  • 超预算还能找到构造超过快照预算的记忆，验证分页／关键词补查及正文命中。
  • 换客户不会串事实跨所、跨客户、跨律师、归属变化与共享批准失效都有负向用例。
  • 学习失败不假报成功consult 拒写、版本冲突、存储失败、后台重放与改稿出处分别核对。
  • 正文只存在数据库无独立记忆 .md 或索引文件；正文更新后目录正确刷新，事务失败无半条记录。
  • 迁移不改变旧资产含义核对 ID、正文、出处、状态与共享批准；旧所级和未判清分类的记录不被丢弃或自动转正。

验证分层：纯逻辑／假模型回归 → 假 CLI＋本轮随机 PG 验事务和权限 → 另行授权的真实模型任务评测。比较首答等待、工具轮次、实际应用与漏召回，不能只用“没有 picker 了”宣称总成本下降，也不能把替身测试说成真实模型质量验收。

最终结论：一个 PostgreSQL 记忆库，实体归属＋业务类别两条分类轴；目录由数据库查询生成，正文按需读取，所有保存／学习走同一受限服务。借鉴 Claude Code 的使用机制，不复制文件存储与灰度 Dream，更不删除律枢业务安全边界。
